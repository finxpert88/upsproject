# UPS Fleet · FSD 修订2静态交互原型

基线：`doc/planning/UPS-Fleet-FIN-POD-FSD-v0.1.md`，v0.1 修订2，2026-09-14 已批准。

## 打开

直接双击 `UPS-Fleet-Prototype.html`。该文件内嵌全部 CSS 与 JavaScript，无 CDN、字体下载或服务端依赖。`index.html` 为同一原型的拆分资源入口，便于继续修改。

## 页面及交互

- 设备总览：授权站点/名称位置/通讯/模式/严重度筛选、分类统计、50/100分页、详情返回、新严重风险提示。
- 设备详情：通讯、供电、风险三轴；续航及需求；风险/覆盖解释；电池串、模块、SOC/SOH、实测负载、额定基准、电力电子、环境、旁路、维护、告警；温度偏好。
- 历史：1h/24h/7d/自定义窗口、最多4条、不同单位分图、缺口、范围带、映射边界、单样本、无历史、权限/服务/部分失败状态。
- 告警：活动/全部事件、筛选、时间线、单条确认备注、已确认仍活动、纯事件无确认、并发已确认、未知结果与投影待同步。
- 配置：注册、能力、映射、历史/规则/计划、校验、发布六步；本地草稿；字段约束；发布差异、冲突、失败和新版本恢复草稿。
- 验收：必要证据项、证据引用、版本匹配与 ready/accepted 状态。
- 诊断、审计、规格对照：版本与闸门、未决操作、只读审计及查询窗口、FSD追踪入口。

顶部“评审场景”提供正常、60+设备分页、空态、加载、离线、局部失败、告警源失败、超量程、游标过期、确认异常、发布异常、会话过期等22个固定场景。

## 建议评审顺序

1. 总览 → UPS-A01 → 风险依据 → 电池/负载历史。
2. 告警 → 单条确认，先提交空备注，再填写备注；观察活动状态不变。
3. 顶部选择“确认结果未知”，确认其他未确认告警，进入只读核对流程。
4. 工程配置 → 修改Q=0 → 校验阻断；改回15 → 校验 → 发布预览 → 发布 → 接入验收。
5. 分别用“提交前失败”“提交后激活失败”观察保留旧版与关闭闸门的区别。
6. 切换“查看者 · B站点”，检查A站点数据消失、工程入口隐藏、无确认权限。
7. “60+设备分页”场景检查翻页；“会话过期”检查内容清除。

## 实现与验证边界

这里的“对应FSD”指静态页面的信息、入口及交互状态对照，不等于已经实现或验收完整生产系统。固定夹具不代表任何实际UPS，历史曲线是示意数据，来源认证、历史读取、告警权威回读、幂等/原子事务、权限服务、持续规则评估、真实自动刷新、容量/性能、FIN版本绑定均未实现。

本原型使用原生 HTML/CSS/JavaScript，便于单文件离线评审；保留原设计的深色工业仪表盘风格。FSD D-02 的生产 Ractive 模块化方向仍需在正式前端实施中落实，不能把本文件当作已完成的 FIN POD 前端。

`verify.cjs` 是 Node VM 下的逻辑及渲染标记检查，不是浏览器DOM/视觉或FIN集成测试。运行：`node verify.cjs`。结果保存于 `verification.json`。

浏览器安全策略拒绝本地文件导航，本轮未完成真实浏览器视觉、移动尺寸和键盘操作验证。CSS已提供响应式断点、焦点样式和减少动画支持，但不能将源码存在这些规则称为实测通过。

原型确认/发布/审计保留在内存，刷新重置；只有草稿与温度偏好保存到本地浏览器。用户修改源文件后运行 `node build.cjs` 重新生成单文件。
